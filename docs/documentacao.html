1. O projeto

A MoveSaúde conecta pessoas com deficiência, idosos e pacientes em tratamento contínuo a uma rede de prestadores verificados de transporte acessível, assistido e de remoção não emergencial. A API, em Java 25 com Spring Boot 4.1 e PostgreSQL, faz a triagem da modalidade pelas necessidades do passageiro, o matching com até três opções compatíveis, a cotação por trecho e a aplicação dos créditos mensais do convênio.

O tema Cidades ESG Inteligentes aparece nos indicadores que a própria API calcula em GET /api/esg/indicadores:

PilarIndicadores
Ambientalkm rodados, CO₂ emitido e evitado pela frota elétrica ou híbrida, % da frota limpa
Socialcorridas acessíveis ou médicas, idas a tratamentos contínuos (hemodiálise, oncologia, terapia), passageiros atendidos, valor subsidiado pelos convênios
Governança% de prestadores verificados (só eles recebem corridas), comissão única e preço detalhado linha a linha

2. Pipeline CI/CD

Ferramenta: GitHub Actions (.github/workflows/ci-cd.yml), com GitHub Environments (staging e production) e GitHub Container Registry. Destino do deploy: Render, com os dois serviços descritos como código no Blueprint render.yaml.

1 · Build e testesJDK 25 + cache Maven, mvn verify: compila, roda os 37 testes e gera o .jar
→
2 · Imagem Dockerbuild multi-stage, sobe API + PostgreSQL com Compose, smoke test, push no GHCR
→
3a · Deploy stagingpush em develop: deploy hook, espera o commit no ar e roda smoke test com escrita
/
3b · Deploy produçãopush em main: aprovação do environment, deploy hook, espera o commit e smoke test somente leitura

Etapas e lógica

JobGatilhoO que faz
Build e testes automatizadostodo push e PR em develop/mainactions/setup-java (Temurin 25) com cache do Maven; ./mvnw -B verify; publica relatórios de teste e o .jar como artefatos; escreve a tabela de testes no resumo da execução.
Imagem Docker e teste com Docker Composeapós o job 1docker build --build-arg GIT_SHA=…; docker compose up com API + PostgreSQL; espera o health check healthy; roda scripts/smoke-test.sh com um fluxo completo de corrida; em pushes, publica no GHCR com as tags sha-<commit>, <branch> e staging/production.
Deploy em stagingpush em developAciona o deploy hook do serviço de staging (secret RENDER_DEPLOY_HOOK_STAGING); scripts/wait-for-deploy.sh espera /api/info responder com o commit testado; smoke test em staging, criando e confirmando uma corrida.
Deploy em produçãopush em mainEnvironment production com revisão obrigatória; deploy hook de produção; espera o commit no ar; smoke test somente leitura.
  • Promoção: o código é integrado em develop e vai automaticamente para staging. Validado, um pull request develop → main leva a mesma versão para produção.
  • Nada vai para um ambiente sem passar nos testes: o deploy automático do Render está desligado (autoDeployTrigger: off), e só o pipeline dispara o deploy.
  • Deploy confirmado de verdade: o pipeline só termina quando a instância nova responde com o commit esperado e passa no smoke test.
  • Segredos fora do código: deploy hooks ficam nos environments do GitHub, e as credenciais do banco nas variáveis do Render.

A API só sobe depois que o banco responde (depends_on: condition: service_healthy). As variáveis vêm do .env, cujo modelo é o .env.example. O Flyway cria o schema e as tabelas e carrega os dados de demonstração na primeira inicialização.

Estratégias

  • Multi-stage: o JDK e o Maven ficam na etapa de build; a imagem final leva só o JRE e o .jar.
  • Cache de camadas: o pom.xml e as dependências vêm antes do código, então uma mudança no código não baixa as dependências de novo.
  • Mesma imagem em todos os ambientes: só mudam as variáveis APP_ENV, DB_URL, DB_USER, DB_PASSWORD, DB_SCHEMA e PORT.
  • Rastreabilidade: GIT_SHA entra na imagem e aparece em /api/info.
  • JVM para containers pequenos: MaxRAMPercentage=60, SerialGC e TieredStopAtLevel=1, para caber nos 512 MB do plano gratuito.

6. Desafios encontrados e como foram resolvidos

DesafioSolução
O protótipo do MoveSaúde era só front-end (React), e a atividade pede Java Spring ou C#.Criamos a API em Spring Boot 4.1 e levamos para Java as regras do protótipo (triagem, cotação, matching e créditos do convênio), cobertas por 37 testes.
O plano gratuito do Supabase permite só 2 projetos ativos, e um já estava em uso.Staging e produção ficaram no mesmo projeto, isolados por schema e usuário de banco: cada usuário é dono só do próprio schema.
A conexão direta do Supabase é só IPv6, e o Render e o GitHub Actions usam IPv4.Conexão pelo pooler Supavisor em modo sessão (compatível com prepared statements do JDBC). Testando, descobrimos que o host certo do projeto é aws-0-us-east-1; o aws-1 respondia "tenant not found".
Criar as senhas do banco sem expor o texto puro.As senhas foram geradas localmente, e só o hash SCRAM-SHA-256 foi enviado ao Supabase. O texto puro fica apenas nas variáveis secretas do Render.
O Jackson 3, padrão do Spring Boot 4, recusava JSON sem campos booleanos opcionais (erro 400).Um teste de integração pegou o erro. Configuramos spring.jackson.deserialization.fail-on-null-for-primitives=false.
O deploy hook do Render é assíncrono: ele aceita o pedido antes de a versão nova estar no ar.O wait-for-deploy.sh compara o commit de /api/info com o SHA do pipeline. Só depois disso roda o smoke test.
O smoke test quebrou porque o JSON do Actuator vem em ordem alfabética.O script passou a consultar endpoints específicos (/actuator/health/db e /readiness), em vez de depender da ordem dos campos.
O plano gratuito do Render tem 512 MB de RAM e hiberna o serviço sem uso.JVM ajustada para containers, timeouts generosos e novas tentativas (retries) nos scripts. A primeira requisição depois da hibernação acorda o serviço.
Testar sem depender de Docker na máquina de desenvolvimento.Os testes usam H2 no modo PostgreSQL com as mesmas migrations. O PostgreSQL real é validado no job do Docker Compose e no Supabase.
